# 首页与用户画像加载期间保持导航响应

## 1. 背景与目标

首页推荐和用户画像从本地全局索引、标签缓存生成内容。用户反馈这些页面加载时无法切换到其他页面。本次目标是让数据准备过程分段让出 JS 执行权，同时保留页面失焦后的异步加载。

## 2. 现状与关键证据

- `src/App.tsx` 将 `BottomNavigationBar` 放在导航栈外，页面加载状态不会主动禁用它。
- `src/hooks/useHomeRecommendations.ts` 在首页获焦时启动异步推荐；失焦清理没有取消进行中的推荐请求，因此设计上会继续加载。
- `src/services/homeRecommendationService.ts` 的 `loadPersonalizationContext` 调用两次同步 `favoriteService.getGlobalIndex`，随后同步遍历全量结果构造视频 ID 和标题集合。
- `src/screens/TagRecommendationsScreen.tsx` 加载画像时使用 `getGlobalIndexYielding` 与 `loadTagProfile`；这些函数会按批次调用 `setTimeout(0)` 让出 JS 执行权。
- 当前静态代码证据说明首页路径存在随索引规模增长的长同步工作；尚无设备 trace 证明它是用户所见导航卡顿的唯一原因。

## 3. 方案与取舍

首页画像上下文复用现有 `getGlobalIndexYielding` 与 `forEachInYieldingBatches`，对可见索引、候选索引和 ID/标题集合构造进行分批处理。网络请求与页面异步任务继续运行，不因页面失焦而取消。

这沿用仓库已有的 JS 线程让出机制，不引入新的线程或依赖。代价是大索引下构造上下文会多经过若干事件循环轮次；换取触摸与导航事件能够穿插处理。

## 4. 风险与影响范围

- 影响首页、画像复用的推荐上下文准备时间和取消时机；不改变索引内容、推荐排序或存储格式。
- 小索引可能多出少量 Promise/定时器开销；应由已有缓存命中路径抵消大多数重复计算。
- 真机上的导航点击响应仍需设备验证。

## 5. 验证方案与结果

- 首页个性化上下文改用 `getGlobalIndexYielding` 获取两份索引，并通过 `forEachInYieldingBatches` 构建 ID/标题集合；画像上下文构造途中检查 `AbortSignal`。
- 全量 TypeScript 检查仍因仓库其他文件报错而退出；筛选输出未发现本次涉及的首页、画像、播放器和同步 store 文件诊断。
- 未新增或运行测试。导航点击响应、切页后加载完成状态仍待真机验证；目前没有帧耗时或设备 trace 数据。

## 6. 当前状态

已完成首页索引读取和全量本地个性化集合构建的分批让出改造。用户画像加载原本已通过 yielding 读取与分批画像生成，且路由失焦时不取消首次读取；本次保留该行为。`BottomNavigationBar` 位于导航容器外，页面加载状态没有禁用它。静态证据指向首页同步扫描是可确认的 JS 阻塞来源，但无法证明它是所有卡顿场景的唯一原因。
