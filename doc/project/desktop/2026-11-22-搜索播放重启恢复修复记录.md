# 搜索播放重启恢复修复记录

## 背景与目标

修复桌面端从搜索页播放歌曲后，重启软件再次播放时持续提示“音频地址已过期，正在尝试重新获取”的问题。目标是让地址刷新次数受控，失败后停止无界循环，并允许用户重新点击播放再次建立解析流程。

## 现状与问题

当前播放队列已经写入 `settings/playback.json`，队列项只保存 BVID、CID、页面和展示元数据；音频文件由 `AudioCacheStore` 按 BVID、CID、音质及实际音轨身份写入索引。搜索队列通过 `PlaybackQueueContext` 保存搜索关键词和页码，因此搜索结果不需要依赖收藏索引才能恢复当前队列。

实际问题出现在播放地址失效后的恢复状态机：

1. HTML 音频元素报告 `code=4` 后，`recoverAfterError` 增加重试次数并重新解析地址。
2. `activateCurrent` 在每次远程解析成功后又把重试次数清零。
3. 如果新地址再次被媒体元素拒绝，状态机永远达不到 `MAX_RETRY_COUNT`，持续发送新的来源并保持“正在重新获取音频地址”。
4. 达到终止状态后仍保留旧 `currentSource`，用户点击播放时可能只是复用失效来源，无法真正重新解析。

日志中同一曲目短时间内连续出现 `audio.source-selected`，与截图中的诊断文案相互印证了上述调用链。

## 方案设计

- 重试预算覆盖“地址解析失败”和“媒体加载失败”两类恢复尝试。
- 只有收到 Renderer 的 `playing` 事件，确认新来源真正开始播放后，才清零重试次数。
- 进入最终错误状态时清除当前来源、缓存标记和重试计数；下一次用户点击播放会重新解析地址，同时保留已保存的播放位置。
- 不持久化短时有效的 CDN 签名 URL，继续使用已有的播放状态文件和音频缓存索引。

## 核心修改

- `desktop/main/runtime/playbackRuntime.ts`
  - 移除缓存命中和远程解析成功分支中的重试计数清零。
  - 在 `playing` 事件中清零重试计数。
  - `failPlayback` 清除失效来源并重置本轮重试状态，支持后续手动重试。
- `tests/unit/playbackRuntime.test.ts`
  - 增加连续地址失败后停止循环的回归测试。
  - 增加终止后手动播放重新解析当前歌曲的回归测试。
  - 补齐测试日志器的 `info` mock，避免测试环境与生产 `AppLogger` 契约不一致。

## 风险与影响范围

- 连续失败达到两次重试后会进入错误状态，避免无限请求；用户仍可点击播放再次尝试。
- 缓存命中、重启进度恢复、切歌进度复位和缓存失效回退逻辑保持不变。
- 真实 Bilibili CDN、Electron HTMLAudioElement 和断网重启场景仍需在目标 Windows 环境手动验收。

## 最终结论

本次故障的直接原因是恢复重试计数在每次地址解析成功后被清零，而不是搜索结果缺少可恢复的队列状态。修复后，搜索歌曲重启播放时的地址刷新路径有明确上限，最终失败可见且可手动重新解析，不会再无限循环。
