# 桌面品牌图标与通知跳转修复记录

## 1. 背景与目标

Windows 任务栏和托盘显示了 Electron 默认图标，桌面端同步通知点击后也没有稳定恢复 NYAMI 主窗口。本次统一桌面运行时图标来源，并让通知点击回到当前客户端窗口。

## 2. 现状与根因

- `BrowserWindow` 没有设置 `icon`，开发模式会使用 Electron 可执行文件的默认图标；安装包虽然配置了 `resource/icon.ico`，运行时仍没有统一读取路径。
- `DesktopShell` 使用内置蓝色 SVG 作为托盘图标，与设计稿中的 `resource/icon.ico` 不一致。
- `Notification` 只创建并显示标题、正文，没有品牌图标和 `click` 事件处理器；窗口隐藏到托盘时，点击通知不会主动恢复 NYAMI 主窗口。

## 3. 核心修改

- 新增 `desktop/main/appIcon.ts`，按开发环境和打包环境解析 `resource/icon.ico`：开发模式读取项目资源，打包模式读取 `process.resourcesPath/resource/icon.ico`。
- `desktop/main/window/createWindow.ts` 将该路径传给 `BrowserWindow.icon`，覆盖任务栏和窗口默认 Electron 图标。
- `desktop/main/tray/desktopShell.ts` 使用同一品牌图标创建托盘，并为通知设置 `icon`；注册通知 `click` 事件，点击后执行已有的窗口恢复和聚焦逻辑。
- `desktop/electron-builder.yml` 将 `resource/icon.ico` 作为 `extraResources` 打入安装包，保证生产运行时路径存在。

## 4. 风险与影响范围

- 图标文件需要随安装包一起发布；若发布产物缺少 `resources/resource/icon.ico`，运行时会回退到候选路径并可能继续显示系统默认图标。
- 通知点击恢复的是当前主窗口，不改变当前播放、同步或页面路由状态。
- 本次未改变 Windows `appId` 和 `setAppUserModelId`，避免破坏已有安装包升级和单实例行为。

## 5. 验证方案与结果

- `npm run desktop:typecheck` 已通过，Electron 类型检查无错误。
- `npm run desktop:build` 已通过，main、preload 和 renderer 产物均生成。
- `git diff --check` 已通过，确认当前差异无空白错误。
- 未在真实 Windows 通知中心和已安装包中手动验证任务栏图标、托盘图标和通知点击；需要在目标 Windows 环境补做实机验收。

## 6. 最终结论

桌面主窗口、任务栏、托盘和 Windows 通知现在共用设计图标；通知点击会恢复并聚焦 NYAMI 主窗口。安装包资源和真实通知中心行为仍需在 Windows 实机补验。
