# 标签同步并发与限流优化

## 1. 背景与目标

收藏标签回填仍需较长时间，歌曲推荐续页也要等待多个画像关键词搜索完成。目标是在保留服务端限流退避能力的前提下提高请求吞吐，并减少标签缓存的小批量事务。

## 2. 现状与关键证据

- `backfillFavoriteTags` 按 `backfillConcurrency` 分批并行请求，原并发值为 3，每批完成后进行一次 SQLite 批量写入。
- 个性化推荐最多使用 5 个画像标签，但搜索并发原值为 3。
- `src/core/http.ts` 中所有 B 站 HTTP 请求共享 `AdaptiveRateLimiter`。原最大速率为每秒 1 次、令牌桶容量为 2；并发升高仍会受该上限约束。
- HTTP 响应中的 412/429 会调用 `reportError(true)`，自适应限速器会将当前速率减半。

## 3. 方案与核心修改

- 将共享自适应限速上限由 1 次/秒调至 2 次/秒，突发容量维持 2；收到 412/429 时沿用既有减半退避机制。
- 标签回填并发由 3 调至 6，因此现有每波结果处理及数据库批量写入也由最多 3 条扩大到最多 6 条。
- 推荐关键词搜索并发由 3 调至 5，使最多 5 个画像关键词均能同时进入请求队列。

## 4. 风险与防护

- 限速配置作用于所有 B 站 HTTP 请求，而不只标签接口；可能增加短时请求密度。412/429 会触发自动降速，但未在本次工作中通过真实账号验证服务端阈值。
- 速率和并发是吞吐上限，不代表实际同步耗时必然按比例缩短；网络延迟、B 站响应和 SQLite 写入仍会影响结果。

## 5. 验证

- 静态检查确认标签工作池与关键词搜索从配置读取并发，且 HTTP 412/429 会触发自适应减速。
- 未运行测试、构建、lint 或真实设备/账号基准；实际耗时变化待设备验证。

## 6. 进一步提高回填吞吐

- 用户反馈标签同步仍慢后，将回填请求并发由 6 提到 12，并将外层工作窗口从每 6 条扩至每 24 条；每 12 个结果仍单独批量写入并报告进度，避免把数据库事务和 UI 进度也延迟到 24 条结束。
- 共享自适应限速上限由每秒 2 次提高到 3 次，突发令牌容量保持 2；412/429 仍会自动将速率减半。缓存读取仍按 500 个 BVID 分块，不触碰 SQLite 参数上限。
- 这是请求吞吐上限配置变化，不是实测耗时结果；限速作用于全局 B 站 HTTP 客户端，且真实账号阈值未验证。
- 代码静态检查应确认批处理不超过 24 个排队项、单次请求并发不超过 12、缓存写入每批不超过 12；未运行测试、构建、lint 或设备基准。
