# 标签同步并发与限流优化

## 1. 背景与目标

收藏标签回填仍需较长时间，歌曲推荐续页也要等待多个画像关键词搜索完成。目标是在保留服务端限流退避能力的前提下提高请求吞吐，并减少标签缓存的小批量事务。

## 2. 现状与关键证据

- `backfillFavoriteTags` 按 `backfillConcurrency` 分批并行请求，原并发值为 3，每批完成后进行一次 SQLite 批量写入。
- 个性化推荐最多使用 5 个画像标签，但搜索并发原值为 3。
- `src/core/http.ts` 中所有 B 站 HTTP 请求共享 `AdaptiveRateLimiter`。原最大速率为每秒 1 次、令牌桶容量为 2；并发升高仍会受该上限约束。
- HTTP 响应中的 412/429 会调用 `reportError(true)`，自适应限速器会将当前速率减半。

## 3. 方案与核心修改

- 将共享自适应限速上限由 1 次/秒调至 2 次/秒，突发容量维持 2；收到 412/429 时沿用既有减半退避机制。
- 标签回填并发由 3 调至 6，因此现有每波结果处理及数据库批量写入也由最多 3 条扩大到最多 6 条。
- 推荐关键词搜索并发由 3 调至 5，使最多 5 个画像关键词均能同时进入请求队列。

## 4. 风险与防护

- 限速配置作用于所有 B 站 HTTP 请求，而不只标签接口；可能增加短时请求密度。412/429 会触发自动降速，但未在本次工作中通过真实账号验证服务端阈值。
- 速率和并发是吞吐上限，不代表实际同步耗时必然按比例缩短；网络延迟、B 站响应和 SQLite 写入仍会影响结果。

## 5. 验证

- 静态检查确认标签工作池与关键词搜索从配置读取并发，且 HTTP 412/429 会触发自适应减速。
- 未运行测试、构建、lint 或真实设备/账号基准；实际耗时变化待设备验证。

## 6. 进一步提高回填吞吐

- 用户反馈标签同步仍慢后，将回填请求并发由 6 提到 12，并将外层工作窗口从每 6 条扩至每 24 条；每 12 个结果仍单独批量写入并报告进度，避免把数据库事务和 UI 进度也延迟到 24 条结束。
- 共享自适应限速上限由每秒 2 次提高到 3 次，突发令牌容量保持 2；412/429 仍会自动将速率减半。缓存读取仍按 500 个 BVID 分块，不触碰 SQLite 参数上限。
- 这是请求吞吐上限配置变化，不是实测耗时结果；限速作用于全局 B 站 HTTP 客户端，且真实账号阈值未验证。
- 代码静态检查应确认批处理不超过 24 个排队项、单次请求并发不超过 12、缓存写入每批不超过 12；未运行测试、构建、lint 或设备基准。

## 7. 全局索引与标签回填解耦（2026-09-29）

### 现象与证据

- `syncStore.startSync` 原先在索引同步前启动标签回填，并在索引分页写入时持续把新视频追加到回填队列。标签 worker 并发为 16，索引请求与每视频一次的 tag 请求共用 `AdaptiveRateLimiter`，全局上限为每秒 3 次、突发 2 次。
- 限流器优先级只重排尚未发出的等待请求，无法收回已经发出的标签请求占用的令牌；任何请求收到 412/429 还会将共享速率减半。数据库写入也共用 WatermelonDB writer，因此并行标签缓存批次可能排在索引页 writer 前后。

### 方案与修改

- 索引启动时暂停并取消后台标签回填，等待当前批次结束；索引同步不再回调标签队列，避免页写入过程中持续竞争网络与数据库 writer。应用中的其他 B 站 API 请求仍受共享限流器调度。
- 索引任务以及已排队的后续索引任务全部结束后，再从稳定的当前账号可见索引快照恢复标签回填。索引成功、失败或用户取消后，只在账号仍匹配且没有其他索引任务运行时恢复。
- 取消中的旧标签任务仅能更新自身状态；通过回填 epoch 校验避免旧任务的迟到中断把新一轮回填再次置为暂停。
- 保留共用的 B 站自适应限流器及每秒 3 次上限，标签请求转到索引完成后的后台阶段；不以拆分限流桶的方式叠加请求额度。

### 验证与取舍

- 定向 ESLint 0 错误，`git diff --check` 通过；全仓 TypeScript 检查未报告本节修改文件错误，仍受根目录 `trackPlayer_backup.ts` 的既有缺失模块和隐式 `any` 错误阻断。未运行测试、构建或设备同步基准。
- 索引同步阶段不再和标签回填争用 API 额度及数据库写入；代价是整轮“索引加标签”的总墙钟时间由并行改为先索引后标签。索引速度改善幅度和真实账号的 412/429 变化尚未实测。

## 8. 标签回填进度与缓存写入（2026-09-29）

### 已确认的吞吐边界

- `biliApi.getVideoTags(bvid)` 当前按单个 BVID 调用视频标签接口；没有发现客户端侧的多 BVID 标签批量接口。
- 标签请求复用 `AdaptiveRateLimiter`，全局配置为每秒最多 3 次、突发容量 2；收到 412/429 会继续自适应降速。因此，在未缓存且每个视频一次请求的当前实现中，100 个视频/秒并非当前 API/限流配置可达到的吞吐，16 个 worker 只提高在途任务数，不提高令牌发放速率。
- 这属于代码路径上限判断，不是 B 站服务端实测；尚未验证是否存在可替换的官方批量标签接口。

### 修改

- 唯一视频与标签缓存预扫描每 200 条让出 JS 执行权，避免大索引扫描长时间占用界面线程。
- 每个标签请求完成后立即更新回填进度，避免原先等待 64 条窗口全部结束后才反映结果。
- 标签缓存结果改为每 16 条批量持久化，末尾及暂停时会刷新余量；远端请求仍使用既有 16 worker、64 条调度窗口和共享自适应限速，未额外叠加请求额度。

### 验证与限制

- 定向 ESLint：0 errors，14 条 curly warnings；`git diff --check` 通过。
- `npx tsc --noEmit --pretty false` 仍被未修改的根目录 `trackPlayer_backup.ts` 缺失模块与隐式 `any` 错误阻断，未发现本次修改文件错误。
- 未运行测试、构建、真机同步或吞吐基准；因此本次可确认的是界面进度更新与缓存落盘更及时，不能声称远端标签请求达到特定每秒数量。若要接近 100 个视频/秒，需要先确认并接入可批量返回多视频标签的受支持接口，再按账号实际 412/429 结果进行压测。
