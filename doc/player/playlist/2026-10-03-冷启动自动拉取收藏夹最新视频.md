# 冷启动自动拉取收藏夹最新视频

## 1. 背景与目标

用户希望每次启动软件时，自动拉取当前收藏夹界面所展示的收藏夹和合集中的最新视频，使全局搜索、推荐等本地索引能在进入软件后自动跟进远端新增内容。刷新时机已确认是**仅冷启动**。

## 2. 现状与排查

- `src/App.tsx` 在认证状态就绪后恢复当前账号的本地全局索引，并恢复账号隔离的待处理收藏变更和索引同步重试；目前不会主动为所有可见播放列表发起最新内容探测。
- `src/screens/FoldersScreen.tsx` 的全局索引目标由未隐藏的自有收藏夹及主页偏好中已选择显示的外部收藏夹/合集构成。`visibleSourceKeysByUid` 和收藏夹可见偏好按账号保存在本机。
- `favoriteService.syncGlobalIndex` 已支持自有及外部来源、并发限制、增量页读取、根据本地已知 BVID 提前结束和 WatermelonDB 持久化；`force` 模式会完整扫描并清理远端已删除视频，不适合每次启动调用。
- `syncStore` 已有按 UID 持久化的全局同步意图与退避重试，可复用于启动任务。

## 3. 方案与取舍

启动时通过现有持久化重试入口发起全局增量同步，并增加 `refreshLatest` 选项，要求已完成同步的目标即使远端视频总数未变，也探测最新页。继续使用现有重叠检测和分页写入：最新页均已知时只请求一页；发现新视频时向后读取，直到与本地数据重叠或到达列表末尾。未完成的分页任务仍优先从 `syncCursor` 续传；首次建立索引或远端总数减少时仍遵循原有全量同步策略。

目标仍只包括未隐藏的自有收藏夹和用户选择显示的外部来源。自动刷新不使用强制全量扫描，不改变外部来源的在线播放和索引写入边界。启动期间同步失败由已有持久队列退避重试；没有任何可见目标时自动模式无操作，手动同步的现有错误语义保持不变。

## 4. 核心修改

- `src/App.tsx` 在认证恢复且当前账号确认后，将账号 UID 记录在进程内的 `Set` 中，每个账号仅在本次应用进程首次恢复时排入一次自动同步；退出再启动后会重新触发。同步意图沿用现有 `queueIndexSyncWithRetry`，网络失败仍使用账号隔离的持久化退避重试。
- `src/store/syncStore.ts` 将 `refreshLatest` 贯穿正在执行后的排队请求及 MMKV 持久重试数据。该字段可选，旧版持久化记录仍按普通索引同步恢复；冷启动任务标记为 `true`。
- `src/services/favoriteService.ts` 对每个可见目标检查最新页。已完成列表会触发增量同步，即使远端总数未变也绕过第 1 页缓存重新请求；发现本地已知 BVID 后复用原有重叠停止逻辑。若存在未完成分页游标，则先请求最新页并原样保留游标，再按原断点续传；新增数据继续写入原有 WatermelonDB 索引。
- 自动模式下没有可见目标时结束为空操作，避免空收藏夹或全部隐藏时进入重试；手动同步和无效外部来源的现有错误处理保持不变。

## 5. 风险与影响范围

- 每次冷启动至少对每个已同步且可见的列表请求最新页；B 站请求频率和网络耗时随可见列表数量增加，受现有并发限制和 API 限流器约束。
- 若发现新增内容，将继续分页到本地重叠点；如果本地还没有索引，或远端数量减少，按原逻辑进行初始/完整扫描，耗时可能明显高于只探测最新页。
- 登录账号、收藏夹可见偏好或网络不可用时的实际设备表现尚待验证。

## 6. 验证

- `git diff --check`：通过。
- 人工审阅调用链：确认自有收藏夹使用现有 B 站收藏夹 API，外部来源继续使用 `ImportedPlaylist`/`sourceKey` 对应 API；最新页探测只绕过第一页缓存，不把 `refreshLatest` 误当成全量 `force`。
- 未运行自动化测试或构建；未进行 Android 真机、冷启动网络请求数量和账号切换验证。

## 7. 最终结果

软件每次冷启动、账号恢复后，会针对当前主页偏好中可见的自有及外部收藏夹/合集拉取最新视频，并通过现有失败重试机制继续处理暂时失败的任务。全量首建和远端数量下降仍按既有逻辑完整扫描。
