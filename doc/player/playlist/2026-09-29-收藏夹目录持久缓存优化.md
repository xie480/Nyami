# 收藏夹目录持久缓存优化

## 1. 背景与目标

收藏夹首页和来源管理页需要读取自有收藏夹目录、已收藏的他人收藏夹及已订阅合集。旧缓存仅保留 10 分钟，用户每次缓存过期后重新进入页面会再次请求 B 站。目标是复用本地目录快照，只有本地操作改变目录或用户主动刷新时才重新构建。

## 2. 现状与关键证据

- `favoriteService.getFolders` 与 `importedPlaylistService.getCollectedPlaylists` 都将目录写入 MMKV，但此前使用 10 分钟 TTL。
- 页面手动下拉时会以 `force=true` 调用服务；创建目录、收藏和取消收藏路径会更新或失效自有目录快照。
- 通用缓存的并发请求去重会复用同 key 的在途请求。旧请求完成时仍可能写回被刷新操作删除的缓存，因此仅删除缓存不足以保证强制刷新后的新结果不被覆盖。

## 3. 方案设计与核心修改

- 通用缓存 TTL 接受 `null` 表示显式失效前不超时，并继续持久化到 MMKV。自有目录与外部来源目录使用该策略；分页视频等短时数据仍保留原 TTL。
- `cache.delete` 与 `deletePrefix` 同时解除匹配的在途请求并增加 key 版本。失效前启动的旧请求即使晚到，也不会写回旧值；其调用方会转接到刷新后的缓存或新请求，并且不会误删后续新请求的去重记录。
- 仅当删除时确有在途请求才增加 key 版本，避免普通缓存删除不断累积版本记录。
- 用户强制刷新先删除旧快照再发起新请求；已知的目录写入路径继续写入回读快照或失效缓存。
- 收藏选择弹窗打开时改为读取缓存，不再将每次打开都当成强制刷新。
- 不自动感知 B 站网页/其他设备上的外部修改；用户可通过手动刷新重建目录，这与需求约定一致。

## 4. 风险与影响范围

- 缓存数据按 UID 区分，显式刷新和本应用内收藏操作负责维护一致性；退出再登录同 UID 时沿用快照。
- 目录快照不再按时间自然过期，若未来新增目录写路径，必须调用对应失效方法或写入新快照。
- 通用缓存失效也会隔离其他 key 的旧在途结果，防止旧数据复活；如果失效发生在读取过程中，等待者最终拿到刷新后的结果。

## 6. 最终结果

自有与已收藏/订阅来源目录可跨应用重启复用本地快照；只有显式刷新或本地目录变更才会重建。分页歌曲缓存仍按既有短 TTL 更新。
