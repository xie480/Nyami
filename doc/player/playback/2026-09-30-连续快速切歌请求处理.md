# 连续快速切歌请求处理

## 1. 背景与目标

用户反馈在播放页快速连续切换歌曲时会出现卡死。目标是串行处理原生队列变更，同时保留切歌操作期间到达的下一首请求，避免并发修改 TrackPlayer 队列。

## 2. 现状与关键证据

- `src/services/trackPlayer.ts` 的 `skipToNextWithPauseRevision` 在读取原生队列、执行音量淡出、切换曲目及必要的逻辑队列水合期间持有 `isSkipping`。
- `isSkipping` 已为真时，后续下一首请求直接 `return`；若 `queueEndRecoveryPromise` 存在，函数等待其完成后也直接返回。这些分支会丢弃用户连续点击的请求。
- 原生队列变更已通过 `withNativeQueueMutation` 串行化。下一首操作还可能等待 `ensureNextLogicalTrackBuffered` 对未缓冲歌曲执行网络水合。
- 上述代码确认了快速点击会被丢弃；没有设备堆栈或日志证明存在原生死锁，因此“实际卡死”的运行时根因仍需真机复现确认。

## 3. 方案与取舍

保留原生队列单飞保护和现有队列版本校验；将上一首、下一首请求排入有界队列，由单一 drain 按触发顺序执行。等待队列恢复或前一曲切换结束时保留请求，不并发调用 TrackPlayer。更换逻辑队列时清空尚未执行的旧请求。

## 4. 风险与影响范围

- 连续点击会依次跳过多首歌曲，完整响应速度受淡入淡出和音频 URL 水合耗时影响。
- 队列末尾或歌曲水合失败时，维持现有错误提示；队列重建后必须清除过期的排队请求，防止误跳新队列。
- 设备侧音频状态、原生队列时序仍需验证。

## 5. 验证方案与结果

- 静态审阅确认每个已出队请求在 `finally` 中释放串行锁并结算 Promise；上一首/下一首失败路径保留原错误提示；queue revision 变化会结算并移除排队请求。
- Android `:app:compileDebugKotlin` 编译通过，但不覆盖播放器 TypeScript 运行行为。全量 TypeScript 检查受仓库既有错误阻断；筛选结果没有本次 `trackPlayer.ts` 诊断。
- 未新增或运行测试。连续快速点击、自然结束与用户切歌竞争，以及真机播放连续性仍待设备验证；没有证据将问题定性为原生死锁。

## 6. 当前状态

已实现有界 FIFO 切歌请求队列，上一首与下一首都由同一个 drain 串行处理。队列长度作为待处理请求上限，队列重建会清掉旧队列请求；自然结束恢复若与用户操作重叠，则延后到当前切歌释放串行锁后处理。用户连续操作可能按顺序跳过多首，单次响应时间仍受淡入淡出及下一首音频水合时长影响。
