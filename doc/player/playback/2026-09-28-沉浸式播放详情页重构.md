# 沉浸式播放详情页重构

## 1. 背景与目标

依据用户提供的 Now Playing 参考图，重构 BiliMusic 当前播放详情页的视觉层：以当前歌曲封面铺设模糊背景，突出旋转唱片、环形频谱、歌曲信息、进度与播放控制，并在底部提供半透明快捷操作区。重构需继续使用现有队列和 TrackPlayer 行为，避免视觉改造改变播放状态和数据来源。

## 2. 现状与已确认能力

- 播放详情页入口和状态协调位于 `src/screens/PlayerScreen.tsx`；播放、暂停、前后切歌、分段播放、播放模式及播放错误重试均有现成服务或 store 接口。
- `src/components/ProgressBar.tsx` 已负责拖动进度和 seek；个性化歌曲的收藏夹选择和队列面板也有现存入口。
- 仓库包含 `useSpectrumPoller` 和 Android 音频 DSP/FFT 原生模块。Android 的播放器音频处理器注入由仓库补丁配置，但本次没有连接设备验证注入和实时数据；iOS 的轮询路径没有实时频谱数据。
- 当前播放能力中没有睡眠定时器服务。参考图的“定时”入口不能接到真实行为，因此本次展示为禁用状态。
- Android 和 iOS 都可以用项目已有原生模块注册方式扩展封面取色，避免引入需要 Expo Modules 的 React Native 封面取色包。

## 3. 方案与取舍

1. 保留 `PlayerScreen` 作为播放数据和动作的协调层，将背景、唱片、频谱环、歌曲信息、播放控制和快捷面板拆成独立组件。
2. 沿用项目已有的 FastImage、BlurView、LinearGradient、Reanimated 和 SVG，不增加 JS 动画/播放器依赖。
3. 封面主题色在原生侧提取，JS 端按封面 URL 缓存最多 48 份结果，并计算对比度、辅助色与动态遮罩。Android 使用 AndroidX Palette；iOS 使用系统 ImageIO/CoreGraphics 采样。网络边界只接受 Bilibili `hdslb.com` / `biliimg.com` 封面域名，HTTP 输入升级为 HTTPS，重定向逐跳校验域名；Android 解码缩小到最长边不超过约 96 像素，双端均限制响应大小和请求时长。
4. Android 环形频谱复用现有轮询 Hook（原生采样间隔 80ms，Hook 已含 EMA），环形组件在样本间插值以平滑视觉变化；iOS 或频谱不可用时使用低幅度视觉动效，避免将模拟值误认为音频数据。暂停、页面离开、应用进入后台或系统开启减少动态效果时，频谱幅度平滑衰减并停止轮询/持续动画。
5. 歌曲切换时封面背景和唱片封面交叉淡入，主题色在 420ms 内按帧插值；只在可见页面播放动画。短屏内容可滚动，唱片依据可用高度缩小。
6. 不新增计时器业务逻辑；保留底部入口位置和无障碍禁用提示，待后续接入真实定时服务。

## 4. 核心修改

- `src/screens/PlayerScreen.tsx`：重排播放页，接入封面主题、系统安全区、响应式唱片尺寸和减少动态效果状态；播放控制继续调用既有 `trackPlayer` 服务、store、收藏夹、音效页与分段选择。
- `src/components/player/AlbumBackground.tsx`：封面模糊背景、渐变暗角和歌曲切换淡入。
- `src/components/player/VinylRecord.tsx`、`AudioReactiveRing.tsx`：圆形唱片、保持角度的唱片旋转、前后封面交叉淡入和本地频谱环；音频采样间隔插值，暂停时平滑衰减；动画受播放状态、页面焦点、应用前后台和无障碍设置约束。
- `TrackInfo.tsx`、`PlaybackControls.tsx`、`PlayerActionPanel.tsx`：歌曲与收藏、播放模式及控制、队列/音效/分段快捷入口。
- `src/components/ProgressBar.tsx`：沿用 seek 手势，增加主题色轨道、滑块和进度无障碍值。
- `src/native/AlbumPaletteModule.ts`、`src/hooks/useAlbumTheme.ts`、`src/utils/albumTheme.ts`：封面主题取色缓存、过期请求保护、420ms 主题色插值、动态前景/强调色和亮度遮罩。
- `android/app/src/main/java/com/bilimusic/module/AlbumPaletteModule.kt`、`DSPPackage.kt`、`android/app/build.gradle`：注册 Android 取色模块并加入 AndroidX Palette。
- `ios/BiliMusic/AlbumPaletteModule.m`、`ios/BiliMusic.xcodeproj/project.pbxproj`：注册基于系统图像 API 的 iOS 取色模块。
- `__tests__/albumTheme.test.ts`：覆盖深色封面、浅色封面可读性、原生取色不可用时的回退和主题插值。

## 5. 风险与影响范围

- Android/iOS 封面取色只会对 Bilibili 封面主机发起原生 HTTPS 请求，重定向也逐跳校验；缓存按 URL 限制为 48 项，失败结果不长期缓存，且失败时采用主题回退。自定义代理或非 Bilibili 封面域名目前会回退默认主题色。
- iOS 代码已加入项目工程引用，但当前 Windows 环境无法运行 Xcode 编译，仍需在 macOS/iOS CI 验证。
- Android FFT 的源代码和注入配置存在，但本次只有编译验证，没有真机确认数据是否实时到达环形频谱。
- iOS 当前显示的是低幅度动效回退，不跟随实际音频；后续若要跨平台实时频谱，需要补齐 iOS DSP 数据链路。
- 计时入口仍不可用，因为项目没有对应的定时播放服务；本次不伪造计时器行为。
- 未连接 Android 设备，未完成视觉截图对照、实际触摸操作、播放连续性和帧率测量。

## 6. 验证方式与结果

- Android：在 `android` 目录执行 Gradle 任务 `:app:assembleDebug` 成功，生成 `app-arm64-v8a-debug.apk` 和 `app-armeabi-v7a-debug.apk`。构建输出含既有 Android Gradle Plugin/compileSdk 与 SDK 元数据兼容性警告；本次 Android Palette 模块的 Kotlin 编译通过。
- JS 打包：Metro Android bundle 成功生成到 `android/app/build/tmp/now-playing-check/`，确认本次页面模块可由项目 bundler 解析。
- TypeScript/ESLint：本次涉及的 TS/TSX 文件 ESLint 通过；Prettier 检查通过。
- 单测：`npx jest __tests__/albumTheme.test.ts --runInBand`，1 个测试套件、4 个用例通过。
- 全仓类型检查：`npx tsc --noEmit` 仍失败于未改动文件 `src/services/tagRecommendationService.ts`、`src/store/folderDataStore.ts`、`src/store/recommendationStore.ts` 和根目录备份文件 `trackPlayer_backup.ts`。本次改动文件没有出现在 TypeScript 错误列表中。
- `git diff --check` 通过。ADB 未连接任何设备，无法执行 APK 安装及交互检查；iOS 原生工程也未在 Xcode 环境编译。

## 7. 技术价值与后续事项

本次把播放页视觉组件从播放数据协调逻辑中拆开，后续可分别调整动画和布局而不重复实现播放行为；封面取色在原生侧采样并缓存，避免 JS 主线程逐帧进行像素计算；FFT 动画的高频刷新限制在局部环形组件。当前音频数据仍由 80ms 轮询提供，样本插值只改善画面连续性，不会增加音频数据分辨率。视觉性能收益尚未通过设备指标验证，不做 60 FPS 或卡顿改善承诺。

建议后续在 Android 真机上验证 FFT 注入、封面切歌、seek、前后切歌、队列和收藏动作，并对照参考图检查长标题、小屏和深浅封面；在 iOS CI 编译工程；如果产品需要定时功能，先设计并接入真实睡眠定时器服务。

## 8. Android 构建失败复查

- **现象：** 用户的 `npm run android:phone` 在 `:react-native-mmkv:buildCMakeDebug[arm64-v8a]` 失败，Ninja 的 `FindFirstFileExA` 报错指向 `C:\Users\CodexSandboxOffline\.gradle\caches\...\prefab\modules\jsi\include\jsi`，失败发生在 APK 安装之前。
- **根因：** 同一工作区的 React Native CMake/Ninja 派生缓存由不同 Windows 用户目录生成并复用。用户构建使用 `C:\Users\Xie\.gradle`，旧 `.cxx` 缓存中的 Ninja 仍引用 `C:\Users\CodexSandboxOffline\.gradle` 的 React Android Prefab JSI 头文件路径。先清理 MMKV 缓存后，构建通过 MMKV，却在 Reanimated 暴露同类旧路径；清理 Reanimated 后，又在 Screens 暴露同类旧路径。这确认问题不在页面源代码或 ADB 安装，而是多个原生依赖各自保存了旧绝对路径的派生缓存。
- **处理：** 分别清理 `node_modules/react-native-mmkv/android/.cxx`、`node_modules/react-native-reanimated/android/.cxx`、`node_modules/react-native-screens/android/.cxx`。清理前确认这些目录位于工作区 `node_modules` 内、被 Git 忽略且没有 Git 跟踪文件；没有删除全局 Gradle 缓存、依赖源码或项目源文件。重建时将 `GRADLE_USER_HOME` 指向用户实际的 `C:\Users\Xie\.gradle`，使新生成的 CMake/Ninja 文件与用户构建环境一致。
- **构建验证：** 清理后执行 `:app:assembleDebug -x lint -PreactNativeDevServerPort=8081 --stacktrace`，`BUILD SUCCESSFUL in 26s`。MMKV、Reanimated、Screens 的 Debug 原生任务覆盖 `arm64-v8a`、`armeabi-v7a`、`x86`、`x86_64` 并通过，APK 完成打包。仍有 Android Gradle Plugin 8.2.1 对 `compileSdk 35` 的兼容性提醒、SDK XML 元数据提醒和 Gradle 9 弃用提醒，均未阻断本次构建。
- **真机验证边界：** 清理后重跑 `npm run android:phone` 时，脚本在 Gradle 启动前报告没有已授权设备。因此本轮确认了 APK 编译，但没有完成真机安装、启动或页面视觉检查；设备重新连接并授权后可直接重跑该脚本。
