# 沉浸式播放详情页重构

## 1. 背景与目标

依据用户提供的 Now Playing 参考图，重构 BiliMusic 当前播放详情页的视觉层：以当前歌曲封面铺设模糊背景，突出旋转唱片、环形频谱、歌曲信息、进度与播放控制，并在底部提供半透明快捷操作区。重构需继续使用现有队列和 TrackPlayer 行为，避免视觉改造改变播放状态和数据来源。

## 2. 现状与已确认能力

- 播放详情页入口和状态协调位于 `src/screens/PlayerScreen.tsx`；播放、暂停、前后切歌、分段播放、播放模式及播放错误重试均有现成服务或 store 接口。
- `src/components/ProgressBar.tsx` 已负责拖动进度和 seek；个性化歌曲的收藏夹选择和队列面板也有现存入口。
- 仓库包含 `useSpectrumPoller` 和 Android 音频 DSP/FFT 原生模块。Android 的播放器音频处理器注入由仓库补丁配置，但本次没有连接设备验证注入和实时数据；iOS 的轮询路径没有实时频谱数据。
- 首版播放页重构时尚无睡眠定时器服务，因此当时“定时”入口被禁用；后续实现记录见第 9.5 节。
- Android 和 iOS 都可以用项目已有原生模块注册方式扩展封面取色，避免引入需要 Expo Modules 的 React Native 封面取色包。

## 3. 方案与取舍

1. 保留 `PlayerScreen` 作为播放数据和动作的协调层，将背景、唱片、频谱环、歌曲信息、播放控制和快捷面板拆成独立组件。
2. 沿用项目已有的 FastImage、BlurView、LinearGradient、Reanimated 和 SVG，不增加 JS 动画/播放器依赖。
3. 封面主题色在原生侧提取，JS 端按封面 URL 缓存最多 48 份结果，并计算对比度、辅助色与动态遮罩。Android 使用 AndroidX Palette；iOS 使用系统 ImageIO/CoreGraphics 采样。网络边界只接受 Bilibili `hdslb.com` / `biliimg.com` 封面域名，HTTP 输入升级为 HTTPS，重定向逐跳校验域名；Android 解码缩小到最长边不超过约 96 像素，双端均限制响应大小和请求时长。
4. Android 环形频谱复用现有轮询 Hook（原生采样间隔 80ms，Hook 已含 EMA），环形组件在样本间插值以平滑视觉变化；iOS 或频谱不可用时使用低幅度视觉动效，避免将模拟值误认为音频数据。暂停、页面离开、应用进入后台或系统开启减少动态效果时，频谱幅度平滑衰减并停止轮询/持续动画。
5. 歌曲切换时封面背景和唱片封面交叉淡入，主题色在 420ms 内按帧插值；只在可见页面播放动画。短屏内容可滚动，唱片依据可用高度缩小。
6. 不新增计时器业务逻辑；保留底部入口位置和无障碍禁用提示，待后续接入真实定时服务。

## 4. 核心修改

- `src/screens/PlayerScreen.tsx`：重排播放页，接入封面主题、系统安全区、响应式唱片尺寸和减少动态效果状态；播放控制继续调用既有 `trackPlayer` 服务、store、收藏夹、音效页与分段选择。
- `src/components/player/AlbumBackground.tsx`：封面模糊背景、渐变暗角和歌曲切换淡入。
- `src/components/player/VinylRecord.tsx`、`AudioReactiveRing.tsx`：圆形唱片、保持角度的唱片旋转、前后封面交叉淡入和本地频谱环；音频采样间隔插值，暂停时平滑衰减；动画受播放状态、页面焦点、应用前后台和无障碍设置约束。
- `TrackInfo.tsx`、`PlaybackControls.tsx`、`PlayerActionPanel.tsx`：歌曲与收藏、播放模式及控制、队列/音效/分段快捷入口。
- `src/components/ProgressBar.tsx`：沿用 seek 手势，增加主题色轨道、滑块和进度无障碍值。
- `src/native/AlbumPaletteModule.ts`、`src/hooks/useAlbumTheme.ts`、`src/utils/albumTheme.ts`：封面主题取色缓存、过期请求保护、420ms 主题色插值、动态前景/强调色和亮度遮罩。
- `android/app/src/main/java/com/bilimusic/module/AlbumPaletteModule.kt`、`DSPPackage.kt`、`android/app/build.gradle`：注册 Android 取色模块并加入 AndroidX Palette。
- `ios/BiliMusic/AlbumPaletteModule.m`、`ios/BiliMusic.xcodeproj/project.pbxproj`：注册基于系统图像 API 的 iOS 取色模块。
- `__tests__/albumTheme.test.ts`：覆盖深色封面、浅色封面可读性、原生取色不可用时的回退和主题插值。

## 5. 风险与影响范围

- Android/iOS 封面取色只会对 Bilibili 封面主机发起原生 HTTPS 请求，重定向也逐跳校验；缓存按 URL 限制为 48 项，失败结果不长期缓存，且失败时采用主题回退。自定义代理或非 Bilibili 封面域名目前会回退默认主题色。
- iOS 代码已加入项目工程引用，但当前 Windows 环境无法运行 Xcode 编译，仍需在 macOS/iOS CI 验证。
- Android FFT 的源代码和注入配置存在，但本次只有编译验证，没有真机确认数据是否实时到达环形频谱。
- iOS 当前显示的是低幅度动效回退，不跟随实际音频；后续若要跨平台实时频谱，需要补齐 iOS DSP 数据链路。
- 首版重构时未实现计时服务；后续已按第 9.5 节接入播放服务事件与持久化截止时间。
- 未连接 Android 设备，未完成视觉截图对照、实际触摸操作、播放连续性和帧率测量。

## 7. 技术价值与后续事项

本次把播放页视觉组件从播放数据协调逻辑中拆开，后续可分别调整动画和布局而不重复实现播放行为；封面取色在原生侧采样并缓存，避免 JS 主线程逐帧进行像素计算；FFT 动画的高频刷新限制在局部环形组件。当前音频数据仍由 80ms 轮询提供，样本插值只改善画面连续性，不会增加音频数据分辨率。视觉性能收益尚未通过设备指标验证，不做 60 FPS 或卡顿改善承诺。

建议后续在 Android 真机上验证 FFT 注入、封面切歌、seek、前后切歌、队列和收藏动作，并对照参考图检查长标题、小屏和深浅封面；在 iOS CI 编译工程；如果产品需要定时功能，先设计并接入真实睡眠定时器服务。

## 8. Android 构建失败复查

- **现象：** 用户的 `npm run android:phone` 在 `:react-native-mmkv:buildCMakeDebug[arm64-v8a]` 失败，Ninja 的 `FindFirstFileExA` 报错指向 `C:\Users\CodexSandboxOffline\.gradle\caches\...\prefab\modules\jsi\include\jsi`，失败发生在 APK 安装之前。
- **根因：** 同一工作区的 React Native CMake/Ninja 派生缓存由不同 Windows 用户目录生成并复用。用户构建使用 `C:\Users\Xie\.gradle`，旧 `.cxx` 缓存中的 Ninja 仍引用 `C:\Users\CodexSandboxOffline\.gradle` 的 React Android Prefab JSI 头文件路径。先清理 MMKV 缓存后，构建通过 MMKV，却在 Reanimated 暴露同类旧路径；清理 Reanimated 后，又在 Screens 暴露同类旧路径。这确认问题不在页面源代码或 ADB 安装，而是多个原生依赖各自保存了旧绝对路径的派生缓存。
- **处理：** 分别清理 `node_modules/react-native-mmkv/android/.cxx`、`node_modules/react-native-reanimated/android/.cxx`、`node_modules/react-native-screens/android/.cxx`。清理前确认这些目录位于工作区 `node_modules` 内、被 Git 忽略且没有 Git 跟踪文件；没有删除全局 Gradle 缓存、依赖源码或项目源文件。重建时将 `GRADLE_USER_HOME` 指向用户实际的 `C:\Users\Xie\.gradle`，使新生成的 CMake/Ninja 文件与用户构建环境一致。
- **构建验证：** 清理后执行 `:app:assembleDebug -x lint -PreactNativeDevServerPort=8081 --stacktrace`，`BUILD SUCCESSFUL in 26s`。MMKV、Reanimated、Screens 的 Debug 原生任务覆盖 `arm64-v8a`、`armeabi-v7a`、`x86`、`x86_64` 并通过，APK 完成打包。仍有 Android Gradle Plugin 8.2.1 对 `compileSdk 35` 的兼容性提醒、SDK XML 元数据提醒和 Gradle 9 弃用提醒，均未阻断本次构建。
- **真机验证边界：** 清理后重跑 `npm run android:phone` 时，脚本在 Gradle 启动前报告没有已授权设备。因此本轮确认了 APK 编译，但没有完成真机安装、启动或页面视觉检查；设备重新连接并授权后可直接重跑该脚本。

## 9. 后续九项体验需求：分析与实施计划

### 9.1 已确认现状

- 播放详情页使用 React Native + TypeScript；页面协调逻辑在 `src/screens/PlayerScreen.tsx`，唱片、背景、环形频谱、控制区分别位于 `src/components/player/`。
- Android 的音频数据链路为 `DSPAudioProcessor → FFTAnalyzer → AudioDSPModule.getSpectrumData() → useSpectrumPoller → AudioReactiveRing`。原生分析器内部产生 512 个 `[0, 1]` 频段，`AudioDSPModule` 下采样后向 JS 返回 128 个频段；当时环形组件固定 64 根线，最大额外长度为 17dp，且将输入裁剪到 `[0, 1]` 后直接线性映射。
- 模糊强度目前由 `AlbumBackground` 按平台写死为 Android 24、iOS 42；`settingsStore.glassBlurAmount` 控制全局玻璃背景，不能复用为播放页封面模糊设置。
- “定时”动作当前在 `PlayerActionPanel` 中禁用；“更多”仅在当前视频包含多个分 P 时启用，并直接打开选集弹窗。
- 随机模式切换时，队列服务通过 `setQueue` 回写洗牌队列；`setQueue` 会同时覆盖 `originalQueue`，导致回到顺序模式时无法恢复原始顺序。
- 用户画像初始加载页面通过 `Loading` 显示原生驱动的循环动画；画像快照及收藏索引构建仍可能在 JS 渲染/交互路径执行，须继续检查同步计算的实际边界。
- “我创建”的列表封面只从 `visibleGlobalIndex` 中查找首条视频封面；收藏夹目录 transformer 当前没有保留目录封面字段。
- 底部导航采用 Native Stack、禁用转场动画并冻结失焦页面；导航栏是独立于导航容器的应用级组件。后续只做有明确收益依据的局部优化，设备帧率/点击到首帧仍需真机测量。

### 9.3 实施与验证约束

- 每项功能独立检查、独立提交，提交格式沿用仓库历史的 `type: 中文摘要`；不推送远端。
- 先沿用 `doc/player/playback/` 中本记录持续补充各项证据、实现和结果，避免同一轮体验改造散落成多份日志。
- 代码静态检查和 Android 构建可由当前工作区执行；真机当前未连接/授权，导航时延、波形实际音量响应和截图视觉效果需在设备端确认，不以代码审阅代替设备测量。

### 9.4 第 1 项：播放页封面背景模糊度

- **改造：** 新增 `playerArtworkBlurAmount` 持久化设置，默认值 18、有效范围 0–48、步进 2，并在 setter 中做有限值检查与范围/步进归一化。`AlbumBackground` 改为接收该值作为 `blurRadius`，滑动时背景即时重绘；没有复用 `glassBlurAmount`，因此全局玻璃面板设置仍保持独立。
- **入口：** “更多”现在始终可点击，打开播放页专用底部面板；面板中提供带辅助功能读数的模糊滑杆。原多分 P 选集列表迁入该面板，切换分 P 仍调用既有 `playSpecificPart`。
- **验证：** 修改文件的 ESLint 检查通过；全仓 `npx tsc --noEmit` 未报告本次涉及的 TS/TSX 文件错误，但仍失败于既有的 `tagRecommendationService.ts`、`folderDataStore.ts`、`recommendationStore.ts` 和根目录 `trackPlayer_backup.ts` 错误。`git diff --check` 通过。真机模糊观感与持久化重进确认待设备验证。
- **边界：** 本项未改播放器队列、曲目切换和 seek 行为；Android/iOS 实际 `blurRadius` 观感受平台渲染实现影响，当前尚无设备截图验收。

### 9.5 第 2 项：定时暂停当前歌曲

- **改造：** 新增 `src/services/sleepTimer.ts`，将绝对截止时间存入 MMKV，并提供启动、取消、读取和跨服务消费到期状态的接口。定时时长提供 5、10、15、30、45、60 分钟选项，可替换现有倒计时。
- **暂停链路：** 播放服务在 TrackPlayer 的进度事件（配置间隔 0.25 秒）和进入播放状态时检查截止时间；到期后消费唯一 deadline 并调用既有 `pausePlayback()` 渐隐暂停。前台 JS 定时回调作为同一进程下的及时触发路径，页面卸载不会清除模块级计时器。
- **界面：** 底部“定时”按钮打开倒计时面板，可查看剩余时间并取消；播放器动作栏会标记当前是否存在有效倒计时。
- **验证：** UI/service 文件 ESLint 通过，新增 TS/TSX 文件 Prettier 检查通过，`git diff --check` 通过；全仓 TypeScript 错误仍在既有服务/store/备份文件，修改的定时器和页面文件没有类型错误。播放时跨页面与后台到期暂停仍待 Android 真机验证。
- **边界：** MMKV deadline 能跨页面与 JS 页面重挂载保留；后台行为依赖 TrackPlayer 持续发送进度/状态事件，代码路径已接入，但本环境无已授权设备，尚未做息屏实测。

### 9.6 第 3 项：增强唱片环形频谱

- **现状证据：** 环形组件收到了 128-bin Android FFT；旧几何将振幅映射到 `3 + 17 × amplitude` dp，频谱被压在线性小范围内。旧频段位置只取向下取整的单 bin，低频区会有相邻径向线复用相同采样位置。若 Android 原生频谱暂时为空，旧逻辑还会回退到一组循环合成波形，因此无法判断那时显示的是音乐信号还是装饰动画。
- **改造：** 保留 64 根径向线和 Android 原生 FFT；频段索引改为 1.45 次幂分布并对相邻 bin 插值，振幅使用 0.62 次幂曲线以显出较低但真实的差异；最大动态长度从 17dp 增至 36dp，环形外沿扩至封面外约 42dp。为容纳新环宽，同步增大唱片舞台并在小屏尺寸预算中为新增 40dp 预留空间。
- **缺失数据行为：** Android 收不到原生 FFT 时不再显示合成波形，避免将固定装饰节奏误认为实时音频；其他平台仍按既有低幅度回退动画工作。
- **验证：** 修改后的播放页、唱片和频谱文件 ESLint 通过；格式检查和 `git diff --check` 通过；全仓 TypeScript 仍有第 9.4 节记录的既有错误，本项文件没有类型错误。实时 FFT 是否在目标手机随音频明显变化、较大环形是否与小屏信息区冲突，仍需设备验证。
- **边界：** 0.62 次幂会提升低幅值噪声的可见程度；原生 FFT 已有噪声门，但具体听感/可视化噪声需依据真机播放结果微调，当前没有原始 FFT 采样日志可据以量化。

### 9.7 第 4 项：随机模式恢复原播放顺序

- **根因：** `togglePlayMode` 洗牌后调用 `trackPlayer.reorderQueue`；服务再次调用 `playerStore.setQueue`，而 `setQueue` 会将传入的当前队列同时写入 `queue` 和 `originalQueue`。顺序基准因而被随机顺序覆盖。
- **方案：** 将“建立一条新播放队列”和“只同步当前播放顺序”分成两个 store 操作；只有新来源队列重置原始顺序，随机切换、TrackPlayer 重排及播放中的队列增删分别维护当前队列和原始顺序。随机开关增加 revision 防护，快速连续切换时丢弃过期重排任务。
- **验收：** 顺序→随机→顺序恢复同一来源顺序；在随机态插入、移除或追加视频后，顺序恢复包含这些有效队列改动；用户从新来源开始播放时仍建立新的顺序基准。
- **实现：** 新增 `setCurrentQueue`，`loadQueue` 和原生队列重排只同步当前顺序；新 `setQueue` 才创建原始顺序副本。`insertNext` 会在原始顺序中插到当前曲目之后，`removeFromQueue` 同步从两份队列移除，`appendQueue` 同步追加；手动整队仅在顺序模式覆盖顺序基准。更换来源/直接设置播放模式会使过期的异步切换任务失效。
- **验证：** 新增 `__tests__/playerStoreQueueMode.test.ts`，覆盖随机再恢复、快速连续切换和新队列/当前队列分离，3 个用例通过。新增测试 ESLint、变更源码的非 Prettier ESLint 规则检查和 `git diff --check` 通过；全仓 TypeScript 检查没有本项文件错误。`playerStore.ts` 在本次之前就不满足仓库 Prettier 检查（对照 `HEAD` 原文件同样失败），为避免重排无关逻辑未整文件格式化。
- **风险边界：** 已保存且在旧版本中被覆盖的 `originalQueue` 无法从当前随机顺序推回历史顺序；升级后新建或重新载入的来源队列会建立正确基准。当前无 Android 设备，尚未对真实 TrackPlayer 事件与 UI 队列联动做真机复验。

### 9.8 第 5 项：从“更多”打开 B 站视频详情页

- **方案：** 在播放器“更多”面板增加当前视频直达操作；读取当前 TrackPlayer/队列 BVID，严格匹配 BVID 格式后构造固定 HTTPS 主机下的视频页地址，再通过 React Native `Linking.openURL` 交给系统处理。打开失败时给出用户反馈，不使用 WebView 或额外依赖。
- **验收：** 链接使用当前视频 BVID；格式异常时不显示无效入口；已存在的背景模糊设置与分 P 选择继续可用。
- **实现：** 新增 `src/utils/bilibiliVideoUrl.ts`，只接受 `BV` 前缀加 10 位数字/字母的标识并生成 `https://www.bilibili.com/video/{BVID}`。更多面板仅在当前 BVID 有效时展示“打开 B 站视频详情页”；播放器关闭面板后调用系统 `Linking.openURL`，Promise 拒绝时弹出提示。模糊度滑杆和分 P 列表仍在同一面板。
- **验证：** 新增 `__tests__/bilibiliVideoUrl.test.ts`，覆盖有效地址、首尾空白和异常/缺失标识，2 个用例通过。播放器面板、页面、URL 工具和测试 ESLint/Prettier 检查通过；本次文件未出现在全仓 TypeScript 错误列表中；`git diff --check` 通过。实际设备上的默认浏览器/已安装 B 站客户端处理仍待真机验证。
- **风险边界：** URL 主机固定为 HTTPS B 站域名，BVID 不作为主机或任意 scheme 输入；外部打开能力取决于系统链接处理器。本项不改 WebView 登录态或站内播放逻辑。

### 9.9 第 6 项：画像加载波形与页面响应

- **现状证据：** “用户画像”的 Loading 位于页面内容分支内，底部导航由 `App` 在 `NavigationContainer` 旁独立渲染，因此页面布局本身没有覆盖导航触摸区域。Loading 使用原生驱动动画；但中心 7 根波形的错峰仅 45ms，峰值集中在 0.66–1.0，低位缩放到约 8%，幅度层次较弱。加载快照时还会同步筛选全局收藏、对视频去重、解析标签 JSON 并聚合偏好；全局索引变更判断还会生成、排序并序列化整份关系数组。这些循环会占用 JS 事件循环，延迟触摸响应。
- **方案：** 保留原生驱动的装饰动画，将中心律动改为 95ms 错峰、0.48–1.0 不等峰值的更明显波形。收藏索引筛选、全局索引恢复映射、标签缓存去重/解析和画像汇总统一按 200 条一批处理，批次间通过 `setTimeout(0)` 让 JS 事件循环处理导航、手势和其他输入；耗时画像路径传递 `AbortSignal`，页面请求取消后停止后续批次。索引变更判断改为按 BVID 保存文件夹/来源成员的精确映射，避免全量排序和整体序列化；冷恢复索引增加 generation 校验，避免让步期间账号清理/索引更新后再写回过期快照。
- **影响边界：** 分批执行降低单次 JS 连续占用的上限，但会增加批次调度次数；实际触摸到导航切换的时延尚无设备基线和实测，本次只确认代码会周期性交还事件循环，不宣称具体帧率或延迟改善。
- **验证：** 新增 `__tests__/yielding.test.ts`，确认批次间已排队的 timer 能运行，且 `AbortSignal` 会终止后续处理，2 个用例通过。修改文件的非 Prettier ESLint 规则检查通过；`operations.ts` 使用已有规则抑制核对时，其中 6 条未使用 `writer` 报错均位于未改动数据库写入方法。Loading、yield 工具和测试的 Prettier 检查通过；其他大文件在本次修改前的 `HEAD` 版本也不通过 Prettier，因此未整文件重排。`npx tsc --noEmit` 不再报告本次涉及文件错误；全仓仍有 26 条既有错误，集中在 `folderDataStore.ts`、`recommendationStore.ts` 和根目录 `trackPlayer_backup.ts`。`git diff --check` 通过。
- **真机边界：** 没有连接 Android 设备，未实测长列表加载时导航点击时延、动画观感或帧率。批次让步与取消行为由单测覆盖，但它们不等同于真实设备的性能数据。

### 9.10 第 7 项：底部导航切换反馈

- **现状证据：** `App.tsx` 已使用 Native Stack、关闭页面转场并冻结失焦页面；底栏在应用级单独渲染，路由状态通过 UI Store 单独订阅，玻璃栏关闭原生模糊与投影，MiniPlayer 也已做 memo 隔离。当前剩余可见的导航栏反馈中，选中指示动画持续 240ms；点击当前路由仍会向导航器发送一次无变化的 `navigate`。
- **改造：** 精确点击当前路由时跳过无效导航调用；从详情子页点某个主标签时仍导航回该标签根路由。快速切换时先停止尚未完成的指示动画，再以 150ms 原生驱动曲线跟随最新路由，避免指示层继续追赶过期目标。
- **验证：** `BottomNavigationBar.tsx` 定向 ESLint（不包含仓库既有 Prettier 规则）通过；修改文件无 TypeScript 错误；`git diff --check` 通过。该文件在本项修改前的 `HEAD` 也不通过 Prettier 检查，未整文件格式化。
- **风险边界：** 既有 Native Stack、无转场和焦点页面冻结已是当前基线，本次只减少同路由空操作并缩短导航栏高亮反馈；没有设备测量点击到页面首帧时延或 JS/UI 帧率，也无法据此量化整体路由性能提升。

### 9.11 第 8 项：“我创建”收藏夹列表封面

- **根因：** 列表行只从已同步的本地全局视频索引中找封面；账号数据清理或本地尚未完成同步时，索引没有可用视频。点击进入详情后，`VideosScreen` 会在线读取收藏夹视频并用首条有效视频封面渲染大图，所以列表与详情的数据来源不同。
- **改造：** 对进入 FlatList 渲染/预渲染窗口的“我创建”条目，仅当现有来源与本地索引都没有封面时，读取该收藏夹第一页有效视频封面。预览请求不复用按 `mediaId` 持久化的详情页缓存，结果只放在当前登录 UID 对应的页面内存状态；组件离开虚拟列表时取消请求。登录 UID 改变时隐藏旧目录并清空封面快照，防止短暂展示上个账号条目。
- **影响边界：** 每个进入虚拟列表窗口且缺封面的自建收藏夹最多请求一页视频数据；已有本地封面、外部播放列表封面与未进入渲染窗口的条目不新增请求。失败或空收藏夹仍显示原有图标占位。
- **验证：** 新增 `__tests__/favoriteFolderCover.test.ts`，覆盖跳过失效视频、选择首个有效封面及空/空白封面，2 个用例通过。`FoldersScreen` 与服务的非 Prettier ESLint 规则通过，新增工具/测试格式检查通过，修改文件无 TypeScript 错误，`git diff --check` 通过。`FoldersScreen.tsx` 在修改前的 `HEAD` 已不通过 Prettier 检查，未对整页格式化。真机账号切换与 B 站请求响应仍待设备验证。
