# 分P开关生效边界与网络切换恢复策略

## 1. 背景与目标

本次核实设置中的“将分P列表加入播放列表”关闭后仍出现分P，以及分析网络环境变化后需要重新进入软件才能恢复加载的原因。此次只做代码链路核实并提出恢复方案，没有修改播放器和网络业务代码。

## 2. 分P开关链路核实

### 2.1 已接通的部分

- `src/screens/SettingsScreen.tsx` 的 Switch 将 `expandMultiPart` 传入 `setExpandMultiPart`。
- `src/store/settingsStore.ts` 将该值保存在 Zustand 状态中，并通过 MMKV `settingsStore` 持久化。
- `src/services/trackPlayer.ts` 的水合缓存 key 包含设置值；`hydrateVideoUncached` 在首次获取视频信息后读取该开关，为新增 Track 生成分P轨道。
- `loadQueue` 会重置原生队列、添加当前曲目水合得到的轨道，再由 `maintainQueueBuffer` 异步添加后续轨道。
- `src/components/PlaylistPanel.tsx` 另有“展开歌曲以选择某一分P”的嵌套行；它只检查 `item.parts` 和本地展开状态，不读取该开关。点击某行会调用 `playSpecificPart`，这是手动选集入口，不等于把整组分P自动追加到原生队列。

### 2.2 确认的生效缺口

设置变化只更新持久化 store，没有通知播放器更新已建好的原生队列，也不会使正在执行的队列水合任务失效。因而：

1. 开关关闭前已经加入 TrackPlayer 原生队列的分P不会被移除。
2. 关闭时正在进行的水合若已读取到开启状态，完成后仍可将整组分P追加到队列；设置变化没有递增队列 revision，也没有在追加前复核设置版本。

**结论：**UI → store → 新水合逻辑的链路存在；未打通的是“设置变化 → 当前/进行中的播放队列重算”。上述两种时序足以造成关闭后仍有分P轨道待播放的现象。

如果用户指的是播放列表面板里仍能展开并看到分P选择行，则这是另一条 UI 链路：这些行目前不受该开关控制，只是手动选集入口，并不代表整组分P已自动进入原生队列。

另有一个相反方向的不一致：`hydrateVideoUncached` 仅在未命中音频/URL 缓存且没有预先确定 CID 时，才通过无 CID 的视频信息响应取得全部分P并执行展开；已有 `v.parts` 会先选出第一个 CID，缓存命中也会绕过该分支。这意味着开启状态也不保证每条播放入口都能展开。它不解释关闭后残留，但说明该开关目前只覆盖部分水合路径。

若用户在关闭开关后**重新建立播放队列**仍稳定复现分P新增，现有静态链路无法单独解释该现场；还需记录 BVID/CID、队列重建时间，以及水合开始/完成和 `TrackPlayer.add` 时的设置值与队列 revision，以区分旧队列残留、在途任务和其他调用路径。

### 2.3 建议修复

- 将分P设置变化视为队列策略变更，增加独立的设置 revision；关闭时递增 revision，并让水合任务在原生队列写入前核对 revision/当前设置。
- 在原生队列串行写入边界应用新策略：保留当前活动轨道与播放位置，移除尚未播放且由自动展开生成的分P；不删除用户通过“选集”明确选中的当前分P。
- 为自动展开轨道标注来源元数据，以便安全区分逻辑队列中的视频与原生队列里的自动分P。不要仅凭相同 BVID 删除轨道，因为同一视频的多个 CID 共用 BVID。
- 统一缓存命中、已有 `parts`、在线搜索、收藏夹及推荐等路径：先获取/复用完整分P元数据，再按同一设置策略决定是否展开。

## 3. 网络切换恢复现状

- `src/services/netStatus.ts` 当前只将 `NetInfo` 映射为 `wifi`、`cellular`、`none`、`unknown`，且只使用 `isConnected` 与传输类型；传输类型不变时不发事件，也没有纳入 `isInternetReachable`。`init()` 未保存底层订阅的 unsubscribe，也没有重复初始化保护。
- `src/App.tsx` 的网络监听只更新 `isOnline` 并在断网时提示；恢复在线时没有调用任何播放、列表或同步恢复入口。`isOnline` 在 App 中没有其他读取点。
- `trackPlayer.processPlaybackError` 在 `netStatus.type === 'none'` 时设置“恢复网络后可重试”并返回。手动重试入口存在，但网络恢复事件不会调用它。
- `src/store/syncStore.ts` 的全局索引错误重试依赖持久计时器和指数退避，最大间隔一小时；网络恢复不会提前唤醒待重试任务。收藏变更也有持久队列，但网络状态服务没有向该队列发恢复事件。

**结论：**网络变化目前会被部分观察到，但没有贯通到失败请求的恢复调度；当请求已因离线结束后，保持当前 App 进程并恢复网络不会自动重新发起这些工作。

## 4. 推荐的恢复策略

### 4.1 建立统一、去重的网络恢复协调器

让 `netStatus` 暴露标准化状态（是否连接、互联网可达性、传输类型及状态版本），只注册一个底层监听，并提供上一状态和当前状态。对 `none → 可达`、`不可达 → 可达` 以及 Wi-Fi/蜂窝切换做短暂 debounce；每个恢复版本只触发一个 single-flight 协调任务。网络类型仍为 Wi-Fi、但 `isInternetReachable` 从 false 变为 true 时也应触发。应用回到前台时调用一次 `NetInfo.fetch()` 作兜底，避免系统后台挂起期间遗漏变化。

### 4.2 由业务模块提供幂等恢复入口

- **播放：**新增受控的网络恢复入口。只有错误确由网络导致且失败前播放器仍有播放意图时，才重新解析当前 BVID/CID、失效一次旧 URL 并恢复原进度；用户主动暂停或已经换曲时不自动播放。失败沿用有界重试和现有手动重试 UI，不进行无限循环。
- **收藏与全局索引：**网络恢复后立即调用当前 UID 的 `resumePendingBiliMutations` 与 `resumePendingIndexSyncRetry`，让计时器重试提前执行；保持现有 UID 隔离、revision 幂等和退避上限。
- **页面请求：**对仍挂载且当前聚焦的列表/详情页暴露可重入的 `refetch`。只重试因网络失败且仍属于当前页面请求代次的任务；取消旧请求或以 generation token 丢弃晚到响应，避免网络切换前的结果覆盖新状态。
- **预加载/自动缓存：**恢复时只重新调度仍有效的任务，并遵守“仅 Wi-Fi”策略；网络切换时不强行启动不符合用户流量设置的下载。

### 4.3 验收条件

- 飞行模式关闭后，无需退出或重新进入软件，失败的当前播放和已挂起同步可自动恢复。
- 网络恢复时用户主动暂停的曲目保持暂停；切歌/重建队列后旧请求不得覆盖新队列。
- 同一次网络恢复只触发一轮协调任务；Wi-Fi 与蜂窝快速切换不会重复启动同步或下载。
- 互联网可达性在传输类型不变时恢复，也能触发恢复。
- 当前聚焦页面能恢复失败加载；离开页面的请求不会在后台更新过期页面状态。

## 5. 风险与待确认事项

- NetInfo 的“互联网可达”不等于 B 站 API/CDN 可达，恢复动作仍需处理服务器级超时、限流和鉴权错误；它们不能都按网络恢复无限重放。
- 自动恢复播放必须保存失败前的播放意图和队列版本，否则可能覆盖用户暂停/切歌操作。
- 分P开关现象已由静态代码确认存在旧队列与在途水合的失效缺口，但用户现场究竟发生在切换开关前已入队、切换时水合未完成还是关闭后新建队列，尚无设备日志确认。

## 6. 验证范围

本次只进行了源码调用链和 Git 历史审阅；没有在设备上复现分P开关时序，也没有运行测试或构建。实施以上策略后，应覆盖断网恢复、Wi-Fi/蜂窝切换、用户暂停保护、请求去重、队列切换竞争，以及设置关闭发生在水合前/水合中/水合后的回归场景。
