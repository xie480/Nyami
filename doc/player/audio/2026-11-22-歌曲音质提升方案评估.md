# 歌曲音质提升方案评估

## 1. 背景与目标

当前项目已经具备 Bilibili 音频流解析、Android 原生 DSP、Windows AudioWorklet 和离线缓存能力。本次评估回答两个问题：

1. 是否还能获得比当前播放结果更高的源音质。
2. 如何提升听感，同时避免把均衡器效果误认为恢复了压缩音频细节。

本方案区分“源流保真度”和“播放后处理”两条链路。源流决定能够保留多少原始信息，DSP 主要改变频响、动态和空间感，不能从低码率音频中恢复已经丢失的细节。

## 2. 当前现状与关键证据

### 2.1 移动端已经声明高音质选项，但默认值偏低

- `packages/core/src/types/domain.ts` 已定义 `low`、`medium`、`high`、`dolby`、`hires` 五种音质。
- `src/services/audioService.ts` 已建立 `30216`、`30232`、`30280`、`30250`、`30251` 的选择和回退顺序。
- `src/screens/SettingsScreen.tsx` 已展示 Hi-Res、Dolby、高音质、标准、省流，并在界面层做登录和大会员限制。
- `src/store/settingsStore.ts` 的默认 `quality` 仍为 `low`，因此新安装用户默认请求 64 kbps 档位。

### 2.2 高级音轨的请求和解析链路不完整

- `packages/core/src/api/biliApi.ts` 的 `getPlayUrl` 固定发送 `fnval=16`、`fnver=0`、`fourk=1`。
- `packages/core/src/types/bili.ts` 的 `BiliPlayUrlData` 只建模了 `dash.audio` 和 `durl`，没有建模 `dash.flac`、`dash.dolby` 等专用音轨容器。
- `src/services/audioService.ts` 只从 `playUrl.dash.audio` 中挑选音频。即使接口返回了专用无损或杜比音轨，当前代码也可能看不到这些候选项。
- `tests/manual/test_ua.js` 已存在 `fnval=4048` 的对照脚本，但当前共享 API 仍使用 `16`；真实账号、视频和地区下的响应差异尚未在本次评估中重新验证。

因此，移动端的 Hi-Res/Dolby 选项目前不能仅凭界面存在就认定已经稳定生效。

### 2.3 桌面端质量设置没有贯通到解析器

- `desktop/renderer/preferences.ts` 和 `desktop/renderer/App.tsx` 提供了“标准 / 高品质 / 最高可用”设置。
- `desktop/main/audio/biliAudioResolver.ts` 只接受 `low`、`medium`、`high`，默认是 `high`。
- `desktop/main/runtime/playbackRuntime.ts` 使用常量 `AUDIO_CACHE_QUALITY = 'high'` 生成缓存键和缓存请求，没有读取 Renderer 的质量偏好。

桌面端当前可以播放高品质流，但“最高可用”选项不会真正改变主进程的源流选择。

### 2.4 DSP 已有实现，但注入方式需要稳定性验证

- `android/app/src/main/java/com/bilimusic/audio/DSPAudioProcessor.kt` 已实现 10 段 Graphic EQ、8 段 PEQ、Limiter、FFT 和多声道 PCM 处理。
- `android/app/src/main/java/com/bilimusic/audio/EqAudioProcessorAdapter.kt` 已实现 ExoPlayer `AudioProcessor` 适配。
- `patches/react-native-track-player+4.1.2.patch` 通过反射访问 TrackPlayer 内部 `ExoPlayer` 和私有 `audioSink`，尝试注入 `EqAudioProcessorAdapter`。
- 该注入依赖第三方库内部类名、方法名和字段名，且逻辑位于 `node_modules` 的补丁结果中。当前会话没有在真机上确认 `DSPAudioProcessor.process()` 持续收到实际播放 PCM，因此“代码存在”与“每台设备都稳定生效”需要分开看待。

Android 官方 `AudioProcessor` / `DefaultAudioSink` 文档明确说明，处理链作用于 PCM，Passthrough 或 Audio Offload 不经过该处理链。因此 DSP 开启时需要确保播放器走 PCM 路径。

## 3. 可选方案比较

| 方案 | 主要收益 | 改动成本 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- |
| 修正 Bilibili 源流请求与选择 | 直接获得更高码率、Hi-Res 或 Dolby 源流 | 中 | 接口行为和账号权限变化 | **第一阶段推荐** |
| 保留 TrackPlayer，继续使用补丁注入 DSP | 复用现有队列、后台播放和状态逻辑 | 小到中 | 反射和第三方升级容易失效 | 短期可用，但必须加健康检查 |
| 自有 ExoPlayer/Media3 播放服务 | AudioProcessor、PCM、Offload 策略完全可控 | 大 | 迁移队列、通知、锁屏和恢复逻辑 | 长期高音质路线 |
| 实时 AI 超分辨率或“无损修复” | 可能改变部分低码率音频的主观听感 | 大 | 伪细节、延迟、功耗和设备兼容性 | 暂不推荐作为主链路 |

## 4. 推荐设计

### 4.1 阶段一：先让最高源流真正生效

1. 扩展播放响应类型，统一收集 `dash.audio`、专用无损音轨和杜比音轨；保留音轨 ID、MIME、编码、采样率、声道数和带宽等元数据。
2. 将播放请求改为“能力请求 + 本地选择”：优先请求完整 DASH 能力，若接口或账号只返回普通音轨则自动回退；不要把 `fnval=4048` 当作永远有效的保证，必须以实际响应为准。
3. 统一移动端和桌面端的 `AudioQuality` 与优先级：
   - `best`：专用无损 / Dolby / 192 kbps / 132 kbps / 64 kbps。
   - `high`：192 kbps 及以下普通音轨。
   - `medium`、`low`：按带宽和流量意图选择。
4. 移动端默认值从 `low` 调整为 `best` 或 `high`，具体默认值需要结合流量提示决定；设置页明确显示“请求档位”和“实际命中档位”。
5. 将桌面端 Renderer 的质量偏好通过现有设置 IPC 传入主进程，移除 `PlaybackRuntime` 的 `high` 硬编码。
6. 缓存键增加 `bvid + cid + requestedQuality + actualStreamId + codec`，避免同一首歌在权限变化或音轨变化后错误复用旧文件。
7. 播放失败时按“当前音轨 → 同档位备用 URL → 较低兼容音轨”回退，并在解码失败时记录实际 MIME 和音轨 ID。

### 4.2 阶段二：把 DSP 变成可证明的播放链路

短期保留当前 TrackPlayer，增加以下边界：

1. 启动时记录 DSP 注入成功、失败原因和播放器版本；失败时保持原音直通，不阻断播放。
2. 对当前补丁添加版本锁定和构建检查，避免 `react-native-track-player` 升级后静默失效。
3. DSP 开启时禁用 Passthrough / Audio Offload，确保音频先解码为 PCM 再经过 `AudioProcessor`；DSP 关闭时才允许使用设备支持的低功耗输出路径。
4. 优先保持 Float PCM 处理，避免不必要的 Float → PCM16 → Float 往返；Limiter 只在实际增益可能削波时介入。
5. 增加响度匹配和可控 Pre-gain，避免“更响”被误判为“更清晰”；保留 EQ 开关、原音对照和一键恢复。
6. 使用固定 PCM 测试向量验证频响、左右声道隔离、采样率切换、短缓冲和尾部残留；再用同一首歌、同一输出设备、接近响度进行人工 A/B。

如果后续要把音质能力作为长期核心卖点，建议将播放器逐步迁移到应用自有的 ExoPlayer/Media3 播放服务，让 `AudioProcessorChain` 在播放器创建时注入，减少反射访问私有字段的维护风险。该迁移应与当前播放队列、后台服务、通知和恢复状态拆开实施。

### 4.3 阶段三：输出端和高级效果

- 展示当前输出设备和可见的系统音频能力，但不承诺应用可以强制 Bluetooth 使用 LDAC 或实现系统级 bit-perfect。
- 仅在源流和 DSP 基线稳定后评估声场、动态压缩、响度标准化等效果；每种效果都提供独立开关和原音对照。
- AI 超分辨率只作为离线实验功能，不能默认插入实时播放链路。

## 5. 验收标准

### 源流

- 设置选择、实际命中音轨和缓存文件元数据一致。
- 普通账号、登录账号、大会员账号和无专用音轨视频均能按优先级回退。
- 同一 BVID 的不同 CID、质量和实际音轨不会互相命中缓存。
- 解析或解码失败不会把低质量文件错误标记为高质量缓存。

### 播放与 DSP

- DSP 开启时能观察到真实 PCM 处理调用；关闭时为原音直通。
- 44.1 kHz、48 kHz、单声道和立体声均不会串声、削波或产生明显进度漂移。
- 播放、后台、锁屏、切歌、缓存和恢复流程与当前行为一致。
- 在相同响度和同一设备下，A/B 结果分别记录为“源流提升”“音色变化”或“未感知差异”，不以码率单项代替听感结论。

## 6. 风险与未决问题

1. Bilibili 播放接口属于站内接口，音轨字段、权限和返回策略可能变化；完整 DASH 参数需要用真实视频矩阵持续探测，不能只依赖社区资料。
2. Hi-Res/Dolby 的可用性受账号、视频本身、地区和设备解码能力影响；不能保证所有歌曲都有无损或杜比源。
3. Android DSP 的当前注入依赖 `react-native-track-player` 内部实现，第三方版本升级可能导致编译失败或运行时回退到直通。
4. 高码率会增加流量、缓存占用和首帧等待；高复杂度 DSP 会增加 CPU、功耗和发热。
5. 浏览器、系统混音器、Bluetooth 编码和耳机硬件可能成为最终音质上限。

## 7. 最终结论

**可以进一步提高，而且最有确定收益的路径是先修正源流请求、专用音轨解析、质量设置贯通和缓存身份，再验证并稳固 DSP 注入。** 当前不建议先投入实时 AI“补细节”，因为它不能恢复源文件已经丢失的信息，且会引入较高的伪影、功耗和兼容性风险。
