# B 站便捷登录方案与实现记录

## 1. 背景与目标

用户希望 BiliMusic 同时支持账号密码和二维码登录，以便在 B 站要求手机号验证但收不到短信时仍有替代登录路径。本文记录开放平台资质约束、免资质方案取舍和本次实现，以及尚需真机确认的 B 站网页会话行为。

## 2. 当前实现

- 设置页点击登录后显示全局 `LoginModal`；弹窗内嵌加载 `https://passport.bilibili.com/login`，没有显式配置 App-to-App 授权或二维码模式（`src/components/LoginModal.tsx:16-21, 58-68`）。
- 登录成功后从 WebView Cookie 中读取 `SESSDATA` 等字段，并保存到系统 Keychain（`src/components/LoginModal.tsx:24-50`、`src/services/cookieService.ts:21-36`）。应用启动时会读取已存 Cookie 并请求用户信息（`src/store/authStore.ts:59-76`）。
- B 站 API 请求统一注入该 Cookie。收藏夹接口使用 `/x/v3/fav/...`，播放地址使用 `/x/player/wbi/playurl`（`src/core/http.ts:25-32`、`src/services/biliApi.ts:23-64, 67-78`）。
- 当前代码中未发现 `refresh_token` 保存或 Cookie 刷新流程；README 中“Cookie 刷新”的描述与当前实现不一致（`README.md:187-202`）。登录反复出现是否由 Cookie 过期导致，需结合实际设备日志确认。

## 3. 官方授权能力与适配性

哔哩哔哩开放平台提供 Android OAuth SDK：移动应用需先入驻并申请应用，取得 `client_id`、`secret`，SDK 授权后返回 `code`，再换取开放平台 `access_token`。该流程可以实现由 B 站授权页/App 参与的用户授权，不需要第三方应用收集用户密码。[Android 应用接入说明](https://bilibili.apifox.cn/doc-885729)；[账号授权说明](https://bilibili.apifox.cn/doc-7492454)

但公开说明中的 `access_token` 是调用开放平台 API 的凭证；没有说明它能换成网页登录的 `SESSDATA`。因此它不能直接替代当前项目传给 `/x/v3/fav/...`、`/x/player/wbi/playurl` 等请求的 Cookie。已查阅的开放平台文档也没有确认这些现有功能均有可替换的授权 API，覆盖范围仍待逐项核实。

## 4. 方案取舍

| 方案                              | 是否能唤起 B 站 App                    | 能否直接兼容当前 Cookie 请求            | 约束                                                                                                   |
| --------------------------------- | -------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 官方 Android OAuth SDK            | 可以按官方移动授权流程接入             | 不能直接兼容；返回的是 OAuth code/token | 需要开放平台应用资质和权限；若要完整替换登录，需验证并迁移每项 B 站数据接口                            |
| Web 二维码登录                    | 通常由另一台设备上的 B 站 App 扫码确认 | 二维码登录可建立网页 Cookie 会话        | 当前手机无法用同一台设备的相机扫描自己屏幕；相关网页登录接口细节主要来自社区维护文档，稳定性需自行验证 |
| 继续用 WebView 登录并改善会话续期 | 不需要唤起 App                         | 与现有 Cookie API 兼容                  | 当前未实现 refresh-token 刷新；需确认可用的官方续期方式和 Cookie 有效期                                |

## 5. 结论

**推荐保留官方 WebView 账密登录，并增加 B 站 Web 二维码登录；用 B 站网页刷新流程延长 Cookie 会话。**该路线不需要开放平台应用资质，二维码确认成功后能取得当前 API 所需的 Cookie。但二维码必须由另一台设备上的 B 站 App 扫描；它不能实现同一台手机里 BiliMusic 直接唤起 B 站 App 的免资质 SSO。

短信是否送达由 B 站及运营商链路控制。二维码登录在已登录设备上通常能省去再次输入账号密码和短信的步骤，但如果 B 站风控再次要求手机号验证，客户端无法绕过，也不能保证一定不再要求短信。因此产品目标应定义为“提供不依赖短信的替代登录，并在平台要求时给出退路”，不能承诺短信必达或永久不重新登录。

### 推荐实现步骤

1. 保留 `passport.bilibili.com/login` 官方登录 WebView 作为账密入口，不在 React Native 自建密码/短信表单，也不读取或记录用户输入的密码和验证码。
2. 增加“扫码登录”入口，向 B 站网页登录二维码接口申请短时二维码，在弹窗中显示“未扫码 / 已扫码待确认 / 已登录 / 已过期”等状态；关闭弹窗或二维码过期时停止轮询。
3. 扫码成功后，按当前返回协议跟随 B 站 cross-domain ticket，在 WebView Cookie 存储中建立 Cookie；重新读取并校验 `SESSDATA`、`DedeUserID`，再请求 `/x/web-interface/nav` 验证会话，成功后才写入登录状态。
4. 将 Cookie 和轮换的 `refresh_token` 作为一个版本化凭证包写入 Keychain。读取旧版单 Cookie 凭证时做一次兼容迁移。
5. App 启动时先检查当前会话；只有 B 站返回需要刷新时才执行完整刷新链路（生成 `CorrespondPath`、获取 `refresh_csrf`、刷新 Cookie、确认轮换），再把新 Cookie 与新 `refresh_token` 一起持久化。网络错误不清除已有凭证。
6. 账密 WebView 登录成功后，只在 B 站自己的页面上下文尝试读取 `localStorage.ac_time_value`（B 站网页使用的刷新令牌键）；不注入/收集密码或短信验证码。该值是否能在 Android WebView 登录后的最终 origin 读取到，需真机验证；读取不到时登录仍可用，但会话只能保持到 Cookie 失效，二维码登录作为更可靠的可续期入口。
7. 删除当前开发日志中打印完整 Cookie 的分支；Cookie、`refresh_token`、二维码 key、手机号和验证码一律不写日志。

### 方案比较

| 方案                          | 资质要求             | 能否取得当前 API 所需 Cookie | 对短信问题的帮助                                      | 主要限制                                                         |
| ----------------------------- | -------------------- | ---------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------- |
| 官方 OAuth Android SDK        | 需要开放平台应用资质 | 不能直接取得/替代 Web Cookie | 已登录 B 站 App 时可减少手输，但当前业务 API 不兼容   | 用户明确无法申请资质，且需迁移 API，排除                         |
| B 站 Web 二维码 + Cookie 刷新 | 不需要开放平台资质   | 可以，依赖 B 站网页登录会话  | 已登录的另一台设备可扫码确认，通常免再次输入密码/短信 | 需另一台设备；网页登录内部接口非稳定公开契约，近期响应格式有变化 |
| 仅保留当前账密 WebView        | 不需要               | 可以                         | 无法解决未送达的短信                                  | 当前代码没有 refresh-token 持久化/续期，Cookie 失效后需重新登录  |

推荐第二种作为便捷登录主路径，第一种由于资质条件不成立不采用，第三种作为兼容回退。

## 6. 新增需求规格

- **FR-1：**保留现有账号密码登录入口，成功后继续安全保存 Cookie，并让现有收藏、用户信息和播放请求可用。
- **FR-2：**提供二维码登录入口；成功后必须得到现有 API 可用的认证凭证，不能只把 OAuth 页面显示为“登录成功”。
- **FR-3：**遇到手机号验证或收不到验证码时，不得伪造成功或绕过平台验证；应允许用户返回、重试或切换另一种登录方式，并展示可理解的状态提示。
- **AC-1：**选择账号密码登录并成功完成 B 站校验后，应用写入有效凭证、更新用户状态，现有需登录接口可请求成功。
- **AC-2：**选择二维码登录并由 B 站确认后，应用获得可用于现有 Cookie 请求的凭证；若所选授权机制只返回 OAuth token，应在实现前完成接口迁移，不得误存为 Cookie。
- **AC-3：**验证码未送达、二维码过期/取消、用户拒绝授权或网络失败时，应用不标记登录成功，且能回到方式选择并重新发起流程。
- **约束：**项目当前依赖 Cookie 访问收藏夹与播放接口；B 站风控验证由平台决定，客户端不能承诺免验证码。

### 已知约束

用户无法取得 B 站开放平台应用资质，因此按“另一台设备扫码”设计二维码主路径。若场景只有这一台手机，则没有确认可用的免资质同机 SSO 方案；不能把普通 OAuth token 当成 Cookie 使用。

## 7. 风险与待确认

- **已知约束：** 用户无法申请开放平台资质，因此不采用官方 Android OAuth SDK。
- **待真机验证：** Android WebView 登录后是否能在 B 站第一方 origin 读取 `localStorage.ac_time_value`，以及二维码 cross-domain ticket 是否能把最新 Cookie 写入 `CookieManager`。
- **平台限制：** B 站要求手机号验证时，二维码/SDK 授权仍可能遇到平台风控；本项目不能控制短信送达，也不能绕过验证。
- **接口稳定性（高）：** Web 二维码和 Cookie 刷新接口属于社区整理的网页登录内部接口，没有查到稳定公开契约。社区项目记录 B 站在 2026-08 将二维码登录成功响应改为 cross-domain ticket，实际 Cookie 改由跟随链接时的 `Set-Cookie` 下发；集成必须兼容该流程并通过真机验证。[相关修复讨论](https://github.com/public-clis/bilibili-cli/pull/27)
- **续期边界：** `refresh_token` 会轮换，Cookie 与新 token 必须一致保存；refresh token 被撤销、设备风控或账号安全状态变化时仍要重新认证。不能承诺永久免登录。
- **安全风险（中）：** 原请求拦截器和登录弹窗会在开发日志中输出 Cookie 预览或完整 Cookie；日志还能被导出（`src/services/LoggerService.ts`）。本次已移除这些输出。
- **验证情况：** 实现后已对登录组件的依赖链运行定向 TypeScript 检查；完整项目 `tsc` 还会扫描仓库根目录的 `trackPlayer_backup.ts`，该备份文件存在不完整相对引用并产生错误。Android 构建已完成，扫码、短信验证及 Cookie 续期仍需真机验证，详见下文。

## 8. 本次实现

### 核心变更

- `src/components/LoginModal.tsx` 增加“扫码登录 / 账号密码”切换，默认显示扫码。扫码通过 B 站 Web 二维码生成与轮询接口，约每 2 秒查询状态，二维码按 180 秒处理；二维码由本机组件生成，不会上传到外部二维码服务。扫码成功后在可见的 B 站 WebView 中跟随回调票据；若平台要求额外验证，用户可在官方页面完成，再校验 `SESSDATA`、`DedeUserID` 并通过 `/x/web-interface/nav` 确认登录。
- `src/services/biliLoginService.ts` 封装二维码生成、轮询和 Cookie 刷新状态查询；`src/services/biliWebViewBridge.ts` 将按需续期任务交给登录弹窗中的第一方 WebView。
- `src/services/cookieService.ts` 在原 Keychain 服务内保存版本化 Cookie + `refresh_token` 凭证，兼容迁移旧版单 Cookie 记录；仅账号 UID 发生变化时清理账号缓存。刷新令牌只接受受限字符格式，Cookie 和令牌不输出日志。
- `src/store/authStore.ts` 在启动恢复时检查 `/cookie/info`，仅在 B 站明确标记需要刷新时，通过 WebView 执行 `CorrespondPath`、获取 `refresh_csrf`、刷新 Cookie 和确认轮换。新 Cookie 与新令牌一起写回 Keychain；网络失败时保留原凭证并继续校验现有会话。
- `src/core/http.ts` 删除 Cookie 内容、长度和预览日志，避免凭证进入可导出的应用日志。
- `src/config/bilibiliAuth.ts` 集中维护网页登录端点、二维码状态码、请求参数、Cookie 名、刷新令牌格式和 WebView 消息类型；续期脚本将任务 ID 与成功/失败消息绑定，忽略过期任务返回。
- 二维码依赖采用 `react-native-qrcode-svg` 与 `react-native-svg@15.8.0`；项目 RN 0.74.5，对应 SVG 版本最低支持 RN 0.73。Metro 配置启用该二维码库为 RN 0.75 以下提供的 TextEncoder 转换器。[react-native-svg 兼容表](https://github.com/software-mansion/react-native-svg#supported-react-native-versions)；[二维码库配置说明](https://github.com/Expensify/react-native-qrcode-svg#integrating-react-native-qrcode-svg-with-react-native-versions-below-075)

### 实际边界

- 短信由 B 站与运营商决定送达；扫码可在另一台已登录设备可用时减少账密和短信输入，但平台仍可能再次要求手机验证。
- Web 二维码、Cookie 刷新属于网页登录内部接口，社区记录显示 2026-08 的跨域 ticket 响应格式有变化；后续接口变化可能需要适配。二维码回调若停留在验证页面，不会提前标记登录成功，用户可完成验证后手动检查登录。
- 账号密码登录尝试在 B 站第一方页面读取 `localStorage.ac_time_value`。如果 B 站未在 WebView 中保存该值，登录仍可使用，但缺少自动续期能力，Cookie 失效后需重新认证。
- 续期流程依赖 Android WebView 的 WebCrypto、跨域带凭证请求和 CookieManager 同步；构建成功不能替代真机上的真实账号验证。
- iOS 尚未执行 CocoaPods 安装及构建验证；新增的 `react-native-svg` 原生依赖需在 iOS 开发环境完成对应集成检查。
