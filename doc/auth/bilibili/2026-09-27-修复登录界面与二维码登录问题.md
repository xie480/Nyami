# 修复登录界面、二维码异常与账密页空白

## 1. 背景与目标

当前登录弹窗有三个用户可见问题：界面层级较弱；二维码流程报网络错误后没有有效恢复路径；切换账号密码模式时，B 站网页登录页可能空白。目标是在不收集账号密码、不改变 Cookie 与登录验证链路的前提下，改善界面并明确处理加载失败。

## 2. 现状与关键证据

- `src/components/LoginModal.tsx` 的 `selectMode('password')` 会将 WebView 地址设为 `BILIBILI_AUTH_ENDPOINTS.passwordLogin`，密码入口由 B 站官方网页承载。
- 同文件的 `handleWebViewError` 只处理续期和 `qr-ticket`，没有处理 `password` 模式；密码页缺少加载中与加载失败状态，因此 WebView 失败时会留下空白区域。
- 密码 WebView 没有传入 `config.userAgent`，扫码回调和续期 WebView 则有该配置。
- 二维码生成与轮询在同一个 `try/catch` 中运行；异常被统一替换成网络提示。二维码地址为空时，二维码框仍显示加载动画，失败后没有可见的官方网页登录回退入口。
- `src/services/biliLoginService.ts` 直接访问 B 站 passport HTTPS 接口，并设置桌面 User-Agent 和主站 Referer。当前环境没有真实设备请求日志，尚不能确认用户设备上的网络错误来自 DNS、TLS、平台响应还是网络策略。

## 3. 根因与待确认项

**已确认：**密码 WebView 的错误没有被呈现或恢复，足以解释页面加载失败后只看到空白；二维码失败状态被统一折叠，且二维码占位一直转圈，导致用户无法判断生成失败并缺少回退操作。

**待确认：**二维码 HTTPS 请求在用户设备上的底层失败原因。尚无设备日志或当前网络复现，不能据此认定 B 站接口已变更。

## 4. 方案设计与取舍

- 使用现有主题色重新组织登录标题、模式切换与二维码卡片，不增加视觉或网络依赖。
- 保留 B 站官方网页作为账号密码入口；补充 WebView 的 User-Agent、加载状态、HTTP/网络错误提示与重试操作。应用仍不读取密码或验证码。
- 将二维码框的加载、失败、二维码三种状态分开呈现；失败时允许重试，并可转入 B 站官方登录网页继续扫码或选择账号密码。
- 对二维码请求错误做安全、可读的归一化，不在日志或界面暴露二维码 key、Cookie 或原始响应体。
- 保留现有 B 站域名白名单、Cookie 获取和登录校验流程。

## 5. 影响范围与风险

预计修改登录组件与二维码 API 适配器，并在本目录记录结果。二维码及 Cookie 续期使用的网页登录内部接口不是稳定公开契约；应用侧无法修复用户设备完全无法访问 B 站的网络问题，需通过失败提示和官方网页回退保持可用入口。

## 6. 验证计划

完成后检查变更差异、登录模式分支、WebView 错误恢复分支和二维码失败分支。真实二维码生成、网页登录、风控验证与 Cookie 落库仍需在可访问 B 站的 Android 设备上确认。

## 7. 核心修改

- `src/components/LoginModal.tsx`：重排登录标题和模式切换；扫码页改为可滚动卡片布局；二维码请求失败或过期时清除失效图像，显示错误状态，并提供重新生成和打开 B 站官方网页登录的操作。
- `src/services/biliLoginService.ts`：区分二维码生成、扫码状态查询的超时、网络不可达和 HTTP 错误；错误文案不包含请求参数或原始响应体。
- `src/components/LoginModal.tsx`：密码 WebView 显式使用项目 User-Agent；增加加载提示、网络/HTTP 错误界面和重载按钮。账号信息仍只由 B 站官方页面接收。

## 8. 验证结果

- `npx eslint src/components/LoginModal.tsx src/services/biliLoginService.ts`：通过。
- `git diff --check`：通过；仅有仓库换行符规范提示。
- `npx tsc --noEmit --pretty false`：未通过。错误来自未修改的 `src/store/folderDataStore.ts:136`（`number | null` 传给 `number`）以及根目录历史备份 `trackPlayer_backup.ts` 的缺失模块和隐式 `any`；本次修改文件没有出现在错误列表中。
- 未运行测试套件，也未在 Android 真机上完成扫码、密码网页登录或 Cookie 落库验证。二维码服务在用户设备上的底层网络故障原因仍待设备日志确认。

## 9. 结果与后续

登录弹窗现有扫码和账密入口均有明确的加载、错误和恢复界面；二维码请求失败时仍可尝试 B 站官方网页登录。现阶段解决了错误被隐藏和失败后无可操作路径的问题，但不能据此确认用户设备已能直连二维码 API。后续应在出现问题的设备上观察 `passport.bilibili.com` 请求结果，并完成真实网页登录验证。

## 10. 后续复现与根因确认（2026-09-27）

用户补充了可复现现象：二维码生成后提示“不受信任的二维码地址”；在 B 站官方登录页扫码或完成人机验证后，应用未更新登录状态。

- **二维码地址检查：**代码只会在 `isTrustedBiliUrl(qr.url)` 返回 false 时显示该错误。对当前 B 站二维码生成接口进行一次脱敏请求，响应码为 `0`，返回 `https` 地址，主机为 `account.bilibili.com`，且包含二维码 key；没有输出 URL、key 或参数值。该主机按现有 `*.bilibili.com` 规则本应受信任。因此，设备实际返回地址与探测响应不同、或设备运行时 URL 解析不一致仍是待确认项，不能把域名缺失当成已证实根因。
- **登录完成回调：**密码模式仅在 WebView 导航到 `www.bilibili.com`、`m.bilibili.com` 或 `bilibili.com` 时自动读取 Cookie 并验证。密码模式没有“我已完成验证，检查登录”按钮；若扫码/人机验证完成后页面留在 Passport/账号子域，应用没有触发 Cookie 检查的路径。这与“页面完成验证但应用无动作”一致，是已确认的流程缺口。
- **Cookie 同步：**读取登录 Cookie 前没有执行 Android `CookieManager.flush()`，且自动等待窗口约为 1.25 秒。异步 Cookie 写入延迟是可能的次要因素，尚无设备 Cookie 状态证明。

## 11. 本轮修复

- 将登录 URL 主机解析从运行时 `URL` 构造器改为严格 HTTPS 解析；只允许 B 站列明的主域及子域和 443 端口。拒绝二维码地址时只显示主机名或“格式无效”，不会展示二维码 key、URL 参数或 Cookie。
- 账密/官方 WebView 模式新增“我已完成验证，检查登录”操作和确认中状态；检查失败时在按钮上方显示原因，自动跳回主站的检测仍保留。
- Android 读取登录 Cookie 前刷新 WebView CookieManager；等待次数从 5 次增至 12 次，每次 250ms，覆盖约 3 秒的 Cookie 同步窗口。
- 保留原有 `SESSDATA`/用户 ID 校验、登录请求验证和验证失败后恢复旧凭证的处理。

## 12. 验证结果与安全复核

- 脱敏请求当前 B 站二维码生成接口，响应码为 `0`，返回地址主机为 `account.bilibili.com`，含有二维码 key；探测脚本仅输出主机与布尔状态，没有输出地址、key 或其参数值。
- `npx eslint src/components/LoginModal.tsx src/services/biliLoginService.ts src/config/bilibiliAuth.ts`：通过。
- `git diff --check`：通过；Git 提示工作副本换行符将按仓库规则转换。
- `npx tsc --noEmit --pretty false`：仍被未修改的 `src/store/folderDataStore.ts:136` 类型错误和根目录 `trackPlayer_backup.ts` 的缺失模块/隐式 `any` 错误阻断；修改的三个 TypeScript 文件没有出现在错误列表中。
- URL 校验只接受 HTTPS 与标准端口 443，并继续要求主机名精确匹配 B 站主域或其子域。错误提示不包含敏感参数；Cookie 校验和旧凭证回滚顺序未改变。
- 未运行自动化测试或 Android 真机登录。当前接口探测来自开发机网络，不能代替用户设备上的二维码扫码、人机验证和 Cookie 落库验证。

## 13. 结果与后续

现在密码/官方网页登录完成后可手动触发 Cookie 获取和登录验证；二维码地址校验也不依赖可能存在运行差异的 `URL` 构造器，且拒绝原因会安全显示主机。仍需在用户设备验证二维码响应与登录 Cookie，若设备仍拒绝地址，可根据提示中的主机名确认是否为新的 B 站官方域名后再纳入允许列表。
